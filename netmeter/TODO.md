## Done

- 2026-08-28: **the sweep was fighting job control.** `sweep: woke 1 stranded process(es) of node` had been repeating every few minutes: two Ctrl-Z'd terminal sessions each held a stopped `npm exec` with a `node` child, `node` was on the day's app list, and the sweep kept waking a process the user had deliberately put to sleep, which the shell then re-stopped on its next terminal read. Nothing was ever stranded. `stopped_procs()` now carries each process's tty and `sweep_candidates()` splits on it: no controlling terminal is netmeter's business (GUI helpers, launchd daemons), a terminal means a shell owns the stop. The narrow cost, a terminal-launched process netmeter froze and lost the record of, is named rather than hidden: `netmeter paused` counts the jobs it passed over and `netmeter paused --jobs` lists them with the way back. Five new checks, 131 total.

- 2026-08-28: **install.sh could leave the machine with nothing running.** `launchctl bootout` returns before launchd has finished tearing the job down, so the bootstrap a few lines later failed with `Bootstrap failed: 5: Input/output error`, and `set -e` aborted the script between the two agents: no daemon, no bar, and an error message that reads like a warning. Hit live during this session's deploy. `boot_out` now waits for the service to actually leave the domain (5s cap, then tries anyway), `boot_in` retries five times and shouts NOTHING IS RUNNING with the manual command if it still cannot, and the bar's failure no longer takes the daemon down with it.

- 2026-08-28: **Pause All grew a second stage, after the first one froze Cursor.** Pressing Pause All now ramps everything down to `PAUSE_ALL_FLOOR` (5%) of its duty cycle and holds it there; the button becomes **Hard Stop**, the second press that lands the `SIGSTOP`, and pressing that again returns to the hold. The ramp has two landings to match (`land` in the ramp entry: freeze, or settle at the floor), `mode_holds` only claims a freeze under the hard stage, the bar carries a fourth row state ("slow", yellow, switch still on) and a status line naming the stage, and network memory deliberately does not remember `pause_all_hard`, since a hold is a reasonable thing to walk back into and a frozen machine is not.

- 2026-08-28: **the stranded-freeze wave**, from the failure above. Pause All froze 35 processes, Resume All appeared to lift them, and 27 Cursor helpers, five WebKit processes, `cloudd`, `nsurlsessiond` and `parsec-fbf` stayed in state `T` with `netmeter paused` reporting "Nothing is paused". Three defects, all fixed with regression tests (58 checks to 122):
  - `throttle_worker` woke apps only implicitly, via the next period's schedule. `resume-all` emptied `throttled.json` mid-period, the loop took its `continue`, and everything it had just stopped stayed stopped with no record of it; `unfreeze_throttled()` reads the same emptied file, so not even a daemon restart could recover. The worker now holds the pids it stopped in memory and wakes them at the top of every iteration, skipping any a real freeze has since taken over.
  - Nothing ever looked from `ps` back to the bookkeeping. `sweep_orphans()` does: one `ps`, every process in state `T`, matched against apps seen today plus the mode lists, `SIGCONT` for anything no live record claims. Runs on `resume-all`, on `pause-all off`, and once a minute in `reconcile_paused`, so a strand heals within a minute.
  - `resume_all` signalled before clearing and cleared with an unlocked `save_json` against writers that take a lock. It now switches the mode off first, clears under the locks, signals, then sweeps.

- 2026-08-28: **the ramp.** A pause was a `SIGSTOP` and nothing else, which strands an app mid-request and can strand it worse mid-save. A pause now spends `ramp_seconds` (8) on the way down: 25% of the duty cycle, then 5%, then a freeze once the app has gone quiet, with a 30s deadline for one that never does. Applies to a single switch and to Pause All alike; the burst and drain caps deliberately skip it, since 25% of a fast link for eight seconds is tens of megabytes. Driven by the daemon (a CLI that exits in 40ms cannot hold a duty cycle), so with no daemon running the freeze stays immediate rather than being silently dropped. The bar carries a third row state, "(stopping...)", and follows a ramp landing in place while the menu is open. Verified live: 12 seconds from `pause` to frozen.
- 2026-08-28: **Low Data stops the traffic nobody asked for.** `BACKGROUND_DOWNLOADS` names the 21 processes that fetch updates, App Store downloads, iCloud sync and ML assets; Low Data freezes them and lifts them on the way out. Most were in `NEVER_FREEZE` before, which meant the mode would freeze Chrome and let `softwareupdated` pull six gigabytes over a hotspot. The floor now holds only what would break the machine (DNS, `trustd`, the window server, terminals); the downloaders moved out of it and onto the bar's list with switches, so one can be let back through. `update_prefs` is the polite half: the documented user-domain auto-update keys go off with the mode and are restored exactly, "was not set" included (verified by round-trip on a throwaway domain). macOS's own schedule needs root, so the mode names the `sudo softwareupdate --schedule off` line rather than pretending.
- 2026-08-28: **burst cap armed by the situation** (design item 4): whenever Low Data is on or the gateway matches a linked metered network, rather than only inside Low Data. The notification names which one armed it.
- 2026-08-28: **sustained-drain detection** (design item 5): `drain_cap_mb` over `drain_window_min`, read from the completed minutes already in `recent.jsonl`. Off by default. One bleed is one freeze, and an app resumed by hand is not re-frozen inside the same window.

- 2026-08-28: **solo mode retired into Pause All.** Solo was Pause All with the allow list capped at one, so keeping both meant two ways to ask nearly the same question, two enforcement paths, and two exemption lists that disagreed.
