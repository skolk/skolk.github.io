## Done

- 2026-08-31: **per-network usage, and a third scope in the menu to read it in.** Asked for as "how much data has been used per network; I don't care in a coffeeshop's wifi, I do care on Pixi". The tether counter already answered this for the one linked network, so the work was widening it rather than inventing it: `usage.json` keeps per-network totals off the interface plus a per-app split off nettop, keyed by gateway MAC and rolled over on the cap's billing period. Same period on purpose, so on the tether the network line and the cap line describe one span instead of being two truths about one hotspot.

  In the bar, Session | Today becomes Session | Today | Network, all three totals shown at once the way the first two already were, the app list following the selection, and **Reset Session** kept where it was. The control moved onto its own row because three labels do not fit beside the numbers in 348 points. The Network row is labelled with the network's name once it has one and `Network` until then, and carries a coarser floor (10 MB) than a day's list, or a billing period's worth of traffic is thirty rows of system chatter.

  Two bugs found while wiring it: `tether_on` compared gateway MACs raw, so the same latent mismatch that broke the link would have left the cap reading zero with a link that looks correct (normalised now), and the network total was recomputed on every tick including the ones where the MAC would not read, which would have blinked the readout to zero on every wi-fi blip.

  Verified live: interface 22.1 MB against a 20.8 MB per-app split, 94%, inside the expected 85-95% band.

- 2026-08-31: **the tether was linked to a MAC that had never existed as far as netmeter knew, and the advice for fixing it only worked somewhere else.** The cap had counted nothing for 27 days. `tether-here` needs you standing on the hotspot, which is exactly where you are not when you notice, so the warning was unactionable wherever it was read. Three parts:
  - `netmeter tether-link NAME|MAC` links any network memory has seen, from anywhere. It replaces rather than appends, because a stale link is not a second tether, it is the same one under an address the phone stopped using, and leaving it in means a cap that counts whoever inherits that MAC next.
  - `tether_candidate()` matches `tether_name` against the names in memory, so the warning names the network it thinks you meant and hands over the command instead of a place to stand. Deliberately name-based: guessing from the shape of a MAC would be cleverer and wrong the first time a hotspot did not randomise.
  - `mac_norm()`, because `arp` prints `30:23:3:...` and `30:23:03:...` for the same address depending on where it came from, and a link stored in one form never matched memory stored in the other.
  - The "nothing counted in N days" check now ages from the day the link was made, not the period start. Relinking used to clear "linked network never seen" and instantly raise "nothing counted in 27 days", which is true, unfixable, and points at the thing you just fixed; it would have sat there until the period rolled over.

  Relinked live to Pixi (`2e:b8:0:78:fa:3a`, router 10.59.187.218), confirmed with Sean. Both warnings clear, `now.json` publishes an empty `tether_warn`.

- 2026-08-31: **Low Data was running at roughly half the throttle it claimed, and the log had stopped being readable.** Reported as "Cursor and Claude Code are still free in Low Data mode". Measured on the live machine before touching anything: a 25% throttle held Cursor stopped 47% of the time instead of 75%, and the per-process trace was ragged (awake 1.7s, 3.5s, stopped 0.45s, 2.5s) rather than the flat 1-on-3-off the duty cycle is. Four causes, all of them now measured fixed at 72%:

  - **`protected()` ran once per pid.** It sat inside a list comprehension's condition in `signal_pids`, so stopping Cursor's 36 helpers ran a full `ps` 36 times: 500-830 ms per stop, measured, now 13 ms. Every millisecond of it was charged to the app's running half, because the stop deadline is counted from the top of the period.
  - **The sweep was undoing the throttle once a minute.** `sweep: woke 6 stranded process(es) of Claude Helper` had been in the log for days. The throttle held those six under the name `Claude`; the day's table filed them under `Claude Helper`; that name was on the app list, no record claimed it, and the sweep freed them. `node` did the same to Cursor's extension host. The sweep now claims by pid rather than by name, so a busy app's processes are spared under whatever label they carry.
  - **Helpers now fold into their app.** `Claude Helper`, `Granola Helper` and `Signal Helper` join `Cursor Helper` and `Google Chrome` in `FRIENDLY`. One app, one row, one identity for enforcement to agree about.
  - **The duty cycle was giving the app its own bookkeeping.** The wake sat at the top of the loop, ahead of the config read, two state reads and (every five seconds) a pid refresh. The period's clock starts after all of it now.

- 2026-08-31: **network memory remembers the switches, not the settings.** It used to remember the whole lowdata family per network, so all five remembered networks held their own copy of `lowdata_throttle`, `throttle_pct` and `burst_cap_mb` as they stood on the last visit. Edit the throttle list at home, walk into a network last seen in July, and July's copy came back over the edit, silently, with no event anyone would connect to it. `MEMORY_KEYS` is now `lowdata` and `pause_all` and nothing else: memory answers "was this mode on here", config answers "what does this mode do". Explicit profiles are untouched, because pinning one is an act rather than a side effect, and `profile_apply` walks `APPLY_KEYS` so a profile still speaks for the whole family. `config_version` 3 trims the entries on disk; ran clean over the five live ones. `netmeter networks` now dates each entry twice (last seen, and the day its switches last moved), and `networks name MAC LABEL` names one without pinning a policy to it.

- 2026-08-31: **the log was 45% false alarm and had two clocks in it.** 372 of 831 lines were `watchdog: netmeter has stopped reporting` and its all-clear, roughly 80 a day against 576 sleep/wake cycles since the last boot: the machine had slept, not the daemon, and every one fired a notification. The bar now compares its own 2s timer's gap against the daemon's, which is the one thing only the bar can answer, and gives the daemon the usual 60 seconds to be current again after a wake before it counts as silent. Separately, `barLog` wrote UTC with a `Z` while the engine wrote local time into the same file, so a pair of lines about the same second sat seven hours apart and the log read as two interleaved days; one clock now, the local one. And a standing fight (`reconcile: re-froze cloudd, nsurlsessiond`, 113 identical lines) is logged when it changes and restated every 15 minutes with how long it has run, rather than once a minute forever.

- 2026-08-28: **the robustness wave is done, six of six.** The last three landed together:
  - **Stale-daemon watchdog** (item 2). The bar's 2s timer watches `now.json`; 60 seconds without a fresh timestamp turns the readout to `⚠︎`, puts a warning row above the mode buttons it is failing to enforce, and posts one notification naming the consequence ("Low Data is set but not enforced"). One per episode, recovery re-arms in silence. Verified live by booting the daemon out for 75s: one warning, then "daemon reporting again" on its return.
  - **The wake-up race** (item 3). A tick more than 30s after the last one is a sleep or a stall, not a tick. The daemon re-reads the gateway MAC and applies profiles, memory and Low Data freezes before it counts a byte, and drops the counters that would span the gap (minute bucket, cap memory, drain window, the interface reading that would charge a night elsewhere to this network). The part-minute before the sleep is flushed to history under its own stamp rather than binned.
  - **Per-network attribution** (item 6). `tether.json` carries a per-app tally for the billing period, and `netmeter tether` prints it under the header, top 10 by default (`--top 0` for all). The table runs 10-15% under the header because one counts payload and the other counts the interface, which the output says out loud: the header is the bill, the table is who to talk to about it.

- 2026-08-28: **the sweep was fighting job control.** `sweep: woke 1 stranded process(es) of node` had been repeating every few minutes: two Ctrl-Z'd terminal sessions each held a stopped `npm exec` with a `node` child, `node` was on the day's app list, and the sweep kept waking a process the user had deliberately put to sleep, which the shell then re-stopped on its next terminal read. Nothing was ever stranded. `stopped_procs()` now carries each process's tty and `sweep_candidates()` splits on it: no controlling terminal is netmeter's business (GUI helpers, launchd daemons), a terminal means a shell owns the stop. The narrow cost, a terminal-launched process netmeter froze and lost the record of, is named rather than hidden: `netmeter paused` counts the jobs it passed over and `netmeter paused --jobs` lists them with the way back. Five new checks, 131 total.

- 2026-08-28: **Pause All grew a second stage, after the first one froze Cursor.** Pressing Pause All now ramps everything down to `PAUSE_ALL_FLOOR` (5%) of its duty cycle and holds it there; the button becomes **Hard Stop**, the second press that lands the `SIGSTOP`, and pressing that again returns to the hold. The ramp has two landings to match (`land` in the ramp entry: freeze, or settle at the floor), `mode_holds` only claims a freeze under the hard stage, the bar carries a fourth row state ("slow", yellow, switch still on) and a status line naming the stage, and network memory deliberately does not remember `pause_all_hard`, since a hold is a reasonable thing to walk back into and a frozen machine is not.

- 2026-08-28: **the stranded-freeze wave**, from the failure above. Pause All froze 35 processes, Resume All appeared to lift them, and 27 Cursor helpers, five WebKit processes, `cloudd`, `nsurlsessiond` and `parsec-fbf` stayed in state `T` with `netmeter paused` reporting "Nothing is paused". Three defects, all fixed with regression tests (58 checks to 122):
  - `throttle_worker` woke apps only implicitly, via the next period's schedule. `resume-all` emptied `throttled.json` mid-period, the loop took its `continue`, and everything it had just stopped stayed stopped with no record of it; `unfreeze_throttled()` reads the same emptied file, so not even a daemon restart could recover. The worker now holds the pids it stopped in memory and wakes them at the top of every iteration, skipping any a real freeze has since taken over.
  - Nothing ever looked from `ps` back to the bookkeeping. `sweep_orphans()` does: one `ps`, every process in state `T`, matched against apps seen today plus the mode lists, `SIGCONT` for anything no live record claims. Runs on `resume-all`, on `pause-all off`, and once a minute in `reconcile_paused`, so a strand heals within a minute.
  - `resume_all` signalled before clearing and cleared with an unlocked `save_json` against writers that take a lock. It now switches the mode off first, clears under the locks, signals, then sweeps.

- 2026-08-28: **the ramp.** A pause was a `SIGSTOP` and nothing else, which strands an app mid-request and can strand it worse mid-save. A pause now spends `ramp_seconds` (8) on the way down: 25% of the duty cycle, then 5%, then a freeze once the app has gone quiet, with a 30s deadline for one that never does. Applies to a single switch and to Pause All alike; the burst and drain caps deliberately skip it, since 25% of a fast link for eight seconds is tens of megabytes. Driven by the daemon (a CLI that exits in 40ms cannot hold a duty cycle), so with no daemon running the freeze stays immediate rather than being silently dropped. The bar carries a third row state, "(stopping...)", and follows a ramp landing in place while the menu is open. Verified live: 12 seconds from `pause` to frozen.
- 2026-08-28: **Low Data stops the traffic nobody asked for.** `BACKGROUND_DOWNLOADS` names the 21 processes that fetch updates, App Store downloads, iCloud sync and ML assets; Low Data freezes them and lifts them on the way out. Most were in `NEVER_FREEZE` before, which meant the mode would freeze Chrome and let `softwareupdated` pull six gigabytes over a hotspot. The floor now holds only what would break the machine (DNS, `trustd`, the window server, terminals); the downloaders moved out of it and onto the bar's list with switches, so one can be let back through. `update_prefs` is the polite half: the documented user-domain auto-update keys go off with the mode and are restored exactly, "was not set" included (verified by round-trip on a throwaway domain). macOS's own schedule needs root, so the mode names the `sudo softwareupdate --schedule off` line rather than pretending.
- 2026-08-28: **burst cap armed by the situation** (design item 4): whenever Low Data is on or the gateway matches a linked metered network, rather than only inside Low Data. The notification names which one armed it.
- 2026-08-28: **sustained-drain detection** (design item 5): `drain_cap_mb` over `drain_window_min`, read from the completed minutes already in `recent.jsonl`. Off by default. One bleed is one freeze, and an app resumed by hand is not re-frozen inside the same window.
