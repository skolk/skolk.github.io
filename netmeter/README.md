# netmeter

Per-app network usage meter for macOS. The monitoring half of Little Snitch / TripMode, built from `nettop` plus a small Swift menu bar app. Made for working on tethered or metered connections.

## What it does

- **Menu bar readout**: live ↓/↑ speed and the running session total (`↓3K ↑175K · 1.29GB`). KB and MB are whole numbers, so the digits that churn every second never change the item's width and walk it off a crowded bar; GB keeps two decimals because it moves about once an hour. Preferences hides either half independently and can collapse the two rates into one, so the item is as wide as you want it:

  | speed | total | menu bar |
  |---|---|---|
  | on | on | `↓3K ↑175K · 1.29GB`, or `⇅178K · 1.29GB` combined |
  | off | on | `1.29GB` |
  | on | off | `⇅178K` |
  | off | off | `⇅` |

  With both off the item is one glyph, so a stale daemon has to say so inside it: `⇅ …` rather than a bare arrow, which would look the same as a quiet network.
- **Modes**, as buttons at the top of the menu. Clicking one toggles it and leaves the menu open, so you can flip a mode and keep reading the per-app list:
  - **Low Data Mode** is the tethering mode, and it does five things. It posts a notification every 25 MB of session data; freezes whatever is listed in `lowdata_apps`; throttles whatever is listed in `lowdata_throttle`; **stops the background downloaders** outright; and **turns the auto-update checks off**, putting them back when the mode lifts. The first three are deep enough to leave an app usable: freeze for the ones you can do without, throttle for the ones you cannot.

    The last two are about the traffic nobody asked for, which on a hotspot is the expensive kind. `BACKGROUND_DOWNLOADS` names the processes that fetch it: `softwareupdated`, `nsurlsessiond`, `cloudd`, `bird`, `mobileassetd`, the App Store agents, Chrome's Keystone, Sparkle and Squirrel. Most of those used to sit in `NEVER_FREEZE`, which meant netmeter would dutifully freeze Chrome and then watch `softwareupdated` pull six gigabytes of macOS over the hotspot. They are freezable now, one at a time from the menu if you need iCloud back. What stays untouchable is the floor that would break the machine: DNS, TLS validation (`trustd`), the window server, your terminal. The update preferences are the polite half of the same idea: freezing an updater stops this download, telling it not to check stops the next one and the catch-up burst when the mode comes off. macOS's own update schedule lives in a root-owned plist, so `lowdata on` prints the `sudo softwareupdate --schedule off` line rather than pretending it handled that one. Both halves are switchable: `lowdata_background`, `update_prefs`.
  - **Pause All**, under the per-app list, slows everything to a trickle and keeps doing it: an app that launches an hour later is caught the moment it reaches for the network. You then switch individual rows back on, and each switch adds that app to the allow list rather than lasting a single tick, so what you end up with is "only these may talk", built one decision at a time instead of guessed at up front. The allow list survives turning the mode off and on, because the apps worth letting through are the same ones tomorrow; `netmeter pause-all clear` throws it away on purpose. **Resume All** lifts the mode and releases everything.

    **It has two stages, and the first one does not freeze anything.** Pressing Pause All ramps every app down to 5% of its duty cycle and holds it there: slow enough to save the data, alive enough that the editor you pressed the button from keeps working. The button then becomes **Hard Stop**, which is the second press that actually freezes the lot (`SIGSTOP`, windows unresponsive), and pressing it again goes back to the trickle. The single-stage version shipped and lasted about an hour: the first thing it froze was Cursor, mid-session, along with 34 other processes. A hold is the answer to the question you actually ask on a metered link, and a freeze is worth pressing twice for. From the CLI: `netmeter pause-all`, `pause-all hard`, `pause-all soft`, `pause-all off`.

    There are no app exemptions. Cursor and Claude Code go down with everything else, which is survivable precisely because the first stage is a throttle rather than a stop. The only things spared are the system floor in `NEVER_FREEZE` (DNS, the window server, the terminal you would type the undo into) and netmeter itself, since freezing what does the unfreezing leaves no way back. This is why nothing gets an "always allowed" flag: an exception you cannot switch off is not one you chose.

    **Solo Mode retired into this on 2026-08-28.** Solo was the same mode with the allow list capped at one, and keeping both meant two ways to ask nearly the same question, two enforcement paths, and two sets of exemptions that disagreed. `netmeter solo` now prints the two commands that replace it, and anything still carrying solo (config, remembered networks, a live stint, a freeze solo owned) is converted once on the next run.
- **Network profiles**: `netmeter profile-here home-hotspot` pins the current Low Data settings (mode, freeze list, throttle list, burst cap) to the network you are on, identified by its gateway MAC, the same identity the tether counter trusts. Joining that network applies them by itself and leaving restores what they replaced, so the hotspot behind you never depends on remembering to flip a mode. A mode flipped by hand while connected stands for that stint; the profile waits for the next join. The menu carries the same thing as a row in the modes block: "Always Low Data on this network..." asks for a name (SSIDs are location-gated for CLI tools, so you provide one), turns Low Data on, and pins; once pinned the row shows a checkmark with the name, notes "off until rejoin" when you have overridden the mode mid-stint, and clicking it again unpins.
- **Network memory**: every network the daemon sees gets its mode settings remembered, no pinning required. The lowdata family plus Pause All (on or off, and what it was allowing) are written to `~/.netmeter/networks.json` as they change, keyed by gateway MAC, and rejoining a remembered network brings back how it was last used: Low Data comes on at the coffee shop because it was on there last week, Pause All stays off at home because you never block everything at home. Explicit profiles still win where both exist, but only for the keys they pin; memory answers for the rest, which is what keeps a Pause All left on at the previous network from sailing through a profiled join. `netmeter networks` lists what is remembered, `networks rm NAME|MAC` forgets one, `networks off` stops the remembering (entries stay, nothing applies or updates).
- **Menu**: per-app list switchable between Session and Today, each row with an on/off switch that freezes the app (SIGSTOP) until resumed. The list has three depths: the top 3, the top 6, or all twenty. The row under the list steps down through them, and the arrow at its right end jumps straight to the far end, so maximize and minimize are each one click from wherever you are. The depth persists across opens. A frozen app past the fold stays visible even when collapsed, because the switch that unfreezes it must not hide behind the row that lists it. The switch shows **both** totals at once with how long each has been accumulating (`Session ⇅351MB · 3m` / `Today ⇅2.01GB · 8h 59m`), so the other number never costs a click; the selected side is the one in full contrast. **Reset Session** sits under that control, beside the counter it resets, with the session's start time next to it. The running duration is not repeated there, because the control itself already carries it.
- **Recent usage**, at the bottom of the menu: a stacked chart of data used against time over the last 5m / 15m / 1h / 6h / 12h, coloured by app, with the ranked per-app breakdown for the same window underneath. Each column shows *which* apps spent that minute, not just how much went. The table's bars carry the same colours, so it doubles as the legend. Colours are assigned by rank within the current window rather than hashed from the app name: rank assignment can never collide among the apps actually on screen, and the legend sits three pixels below the chart, so it stays correct even though the mapping changes with the window. One column per minute up to sixty, so a 5m window is five fat columns rather than sixty slivers of mostly nothing, and the rightmost column is the last *completed* minute, since the daemon flushes on the clock rollover. Daily totals cannot answer this, because they only ever go up: they tell you who has spent the most since midnight, never who is spending it *now*. Click the window you want; the chevron on the left collapses chart and table together when you don't want the height. Both the window and the collapsed state persist. `ChartView.timeOnX` transposes the plot if you would rather have time run down the side.
- **Window** ("Open netmeter...", at the foot of the menu): Session / Today / Yesterday tables, auto-refreshing, each headed with its span (`running 8h 59m` for a live period, `over 23h 51m` for a closed day).
- **History**: one JSON file per day in `~/.netmeter/`.
- **The burst cap and the drain cap** are the two nets under a surprise download, and they are armed by the situation rather than by a mode: whenever Low Data is on **or** you are on a linked metered network. `burst_cap_mb` freezes anything that moves more than that inside one minute, which is what stops an editor deciding to fetch a 500 MB update. `drain_cap_mb` (off by default; set it to arm it) catches the shape a per-minute cap cannot see: 30 MB a minute for ten minutes never trips a 50 MB/min cap and still costs 300 MB. Neither of them ramps, deliberately. The ramp spends its first seconds at 25% of the duty cycle, and 25% of a fast link is tens of megabytes, so a soft landing for the exact transfer the cap exists to stop would be no cap at all.
- **Pausing ramps down rather than cutting off.** A `SIGSTOP` out of nowhere is a wall: an app mid-request loses the request, and mid-save it can lose worse. So a pause spends a few seconds on the way down instead: 25% of the duty cycle, then 5%, then a freeze once the app has actually gone quiet, with a deadline (`ramp_max`, 30s) for one that never does. The ramp has two landings since Pause All grew its stages: a pause still ends in a freeze, and Pause All's soft stage ends at 5% and stays there, which is the same slope stopping one step short of the wall. Turning off the wifi does not feel abrupt because the app gets to notice; this is as close as a process-level tool can get. It cannot make an app stay alive and offline at the same time, which is the Network Extension line. The menu shows the middle state as "(stopping...)" and updates in place while you watch. Switchable with `ramp`.
- **Throttling**: `netmeter throttle claude --pct 25` duty-cycles an app between SIGSTOP and SIGCONT so it keeps working at a fraction of its speed, rather than stopping dead. This is the control for an app that a freeze would ruin, which is why Claude Code has one and has no freeze switch. It is a soft brake, not a cap: see the note below on what it does and does not hold back.
- **CLI**: `netmeter`, `netmeter session`, `netmeter session reset`, `netmeter pause <app>`, `netmeter throttle <app> --pct 25`, `netmeter throttle <app> off`, `netmeter resume-all`, `netmeter pause-all`, `netmeter pause-all hard`, `netmeter pause-all soft`, `netmeter pause-all off`, `netmeter paused`, `netmeter log`, `netmeter lowdata on|off`, `netmeter profile-here <name>`, `netmeter profile`, `netmeter profile rm <name>`, `netmeter networks`, `netmeter networks rm <name|mac>`, `netmeter networks on|off`, `netmeter recent 60`, `netmeter pause-all clear`, `netmeter display --rate on|off --total on|off --combine on|off`, `netmeter show 2026-07-29`.
- **meeting-mode-extension/**: a tiny Chrome extension (load unpacked via `chrome://extensions`). One click discards every tab except the active one, audible tabs, and meeting domains.

## Install

```sh
./install.sh
```

Copies the engine to `~/bin/netmeter`, compiles the bar app to `~/bin/netmeter-bar` (needs Xcode or CLT for `swiftc`), writes both LaunchAgents, and starts them. They run at every login from then on.

To change the code: edit here, run `./install.sh` again.

## Uninstall

```sh
launchctl bootout gui/$(id -u)/com.seankolk.netmeter
launchctl bootout gui/$(id -u)/com.seankolk.netmeterbar
rm -f ~/bin/netmeter ~/bin/netmeter-bar
rm -f ~/Library/LaunchAgents/com.seankolk.netmeter*.plist
rm -rf ~/.netmeter
```

## Notes that cost a morning to learn

- **To move the readout along the menu bar, hold Cmd and drag it.** A plain drag does nothing, on any menu bar item, which is the whole reason it looks stuck. macOS saves the result to `~/Library/Preferences/netmeter-bar.plist` under `NSStatusItem Preferred Position netmeter`, the key named by `statusItem.autosaveName`. The value is a pixel offset from the right edge, so a larger number sits further left, and it is really a sort key against whatever else is in the bar: macOS rewrites every item's number when the bar reflows, so what persists is the ordering, not the figure. To place it without dragging, stop the app first, or `cfprefsd` writes its cached value back over yours:

  ```sh
  launchctl bootout gui/$(id -u)/com.seankolk.netmeterbar
  defaults write netmeter-bar "NSStatusItem Preferred Position netmeter" -float 305
  killall cfprefsd
  launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.seankolk.netmeterbar.plist
  ```

  Pick the number by reading the neighbours you want to sit between: `defaults find "NSStatusItem Preferred Position"`. Set `autosaveName` explicitly rather than accepting the auto-generated `Item-0`, which is only stable while this remains the app's one and only status item. The preferences domain is the bare executable name and not a bundle identifier, because netmeter-bar is a plain Mach-O rather than a `.app`, so renaming the binary loses the position. Control Center, Spotlight and the clock are pinned and never move.
- **The history is one line per minute, appended, not a rewritten blob.** `~/.netmeter/recent.jsonl` holds `{"m": <epoch minute>, "a": {app: [in, out]}}` and keeps the last 800 minutes. Everything else in `~/.netmeter` is a single JSON file rewritten in place, which is right for state that stays small; for a rolling history it would mean writing hundreds of KB a minute to record a few dozen numbers. Appending is O(1) and pruning happens once an hour.
- **`nettop` sometimes reports a negative interval delta**, presumably when a counter resets mid-sample (`syspolicyd: [0, -28]`, seen 2026-08-19). Summed as-is it walks the daily totals *backwards*, so deltas are clamped at zero rather than trusted.
- **Units are decimal** (1 GB = 10^9 bytes), not binary. A carrier selling a 50 GB plan means 50 x 10^9, so counting the cap in 2^30 handed out 7.4% of phantom headroom: the "100% used" warning did not fire until roughly 3.7 GB past the real cap. Display uses the same units so the bar and the bill agree.
- **Two processes writing one JSON file will eat your settings.** `save_json` wrote through a shared `<path>.tmp`, so a Preferences Save (which fired two `netmeter` calls at once) could interleave into an unparseable `config.json`. `read_json` swallowed the `JSONDecodeError` and returned `None`, `load_config` filled in defaults, and the next write persisted them: one click unlinked a tether network. Fixed three ways, all of which were needed: pid-scoped temp names, an `flock` around every read-modify-write, and an `update_config` that recovers from `config.json.bak` and says so rather than answering a corrupt file with fresh defaults.
- `nettop`'s per-process cumulative counters are **not monotonic**: they sum the currently open sockets, so they drop when sockets close. Never diff them yourself; run `nettop -d` and consume its per-interval deltas.
- `nettop` block-buffers when piped. Run it under `script -q /dev/null` (a pty) to get samples in real time.
- Expect netmeter to read 10-15% below the interface counters (Bandwidth+, `netstat -ib`): packet headers and processes living under one sample interval are invisible to it.
- **Throttling by duty cycle leaks, and it leaks more the shorter the period.** An app stopped for three quarters of every period does not do a quarter of the traffic: the kernel keeps filling its socket buffer while it sleeps, and it drains the backlog at full speed the moment it wakes. Measured against a rate-capped transfer at a 25% setting: 63% of full speed at a 4s period, 84% at 1s, 95% at 0.5s. The throttle only bites once the off-window is long enough to overflow the buffer, which is why the default period is seconds rather than milliseconds, and why `burst_cap_mb` exists. Against CPU, where there is no buffer to hide in, the same cycle is exact: a 25% setting measures 26%, a 5% setting measures 5%.
- **A throttled app is frozen at the moment the daemon dies.** Every exit that runs code releases it (`atexit`, plus explicit SIGTERM/SIGINT/SIGHUP handlers, since launchd stops the daemon with SIGTERM and the default handler skips both `finally` and `atexit`). SIGKILL cannot be handled, so it genuinely does leave the app stopped, about as often as the duty cycle says it should. The cover for that is `unfreeze_throttled()` running on the way *in* as well as out: launchd's `KeepAlive` restarts the daemon a second later and it releases whatever the corpse left frozen.
- **`nettop` counts loopback, the tether counter does not.** A local transfer over `127.0.0.1` shows up in the per-app list and the recent-usage chart at full size, once as sent and once as received, so a 400 MB download from a local server reads as 800 MB that never touched the network. The tether budget is safe from this because it is measured differently, from `netstat -ib -I en0`, the wifi interface only. Worth knowing before a chart spike sends you hunting.
- **A label is not a substring.** `app_pids` matched by `pgrep -f <label>`, which matches anywhere in a command line, so a burst-cap freeze aimed at Signal the messenger also stopped `/Applications/WiFi Signal.app`, and it stayed stopped for four days because nothing ever checked. The label now has to sit on a path boundary: `(^|/)Label([ ./-]|$)`. Both halves of that are load-bearing. Leading `/` alone still swept in Apple's `CursorUIViewService` when freezing Cursor, and the label has to be escaped for the regex besides, because `networkserviceproxy (Apple relay)` is a real one and those parentheses are a capture group otherwise.
- **A duty cycle that loses its bookkeeping mid-period strands everything it stopped.** `throttle_worker` woke apps implicitly: the next period's schedule sent `SIGCONT` to whatever it was about to re-stop. That works right up until there is no next period. On 2026-08-28 `resume-all` emptied `throttled.json` while 35 apps sat in the stopped half of their cycle; the loop read the empty file, took its `continue`, and left every one of them stopped with nothing anywhere recording that they were. `netmeter paused` reported "Nothing is paused" over 27 stopped Cursor helpers, five WebKit processes and `cloudd`, and `unfreeze_throttled()` could not help because it reads the same file that had just been emptied. The worker now keeps the pids it stopped this period in memory and wakes them at the top of every iteration, before it reads anything, skipping any that a real freeze has taken ownership of since.

- **`paused.json` is intent; `ps` is truth, and only one of them was ever consulted.** Every resume path walked the bookkeeping, and `reconcile_paused` can only fix entries that exist, so a freeze no entry describes was invisible and permanent. `sweep_orphans()` walks the other direction: one `ps`, every process in state `T`, matched back against the apps netmeter has watched move bytes today plus its own mode lists, and anything no live record claims gets `SIGCONT`. It runs at the end of `resume-all`, at the end of `pause-all off`, and once a minute inside `reconcile_paused`, so a stranded freeze heals itself within a minute instead of outliving the session. It will not touch a process netmeter has never met, and it steps over anything legitimately stopped (a throttled app is stopped for most of every period by design). It can still wake a job you suspended by hand if that job is an app on today's list; that is the honest cost, and a stranded editor is the more expensive mistake.

- **`resume-all` cleared state files with an unlocked write.** The daemon's `set_paused` takes a lock; `resume_all` used a bare `save_json`, and it signalled first and cleared afterwards, which leaves a window where the daemon is still enforcing a mode it is about to be told is over. Both halves of the 2026-08-28 strand ran through that window. It now switches the mode off first, clears under the same locks the writers use, signals second, and sweeps third.

- **A freeze nobody reconciles outlives what it froze.** `paused.json` only ever changed on an explicit pause or resume, so an app that was frozen, force-quit and relaunched stayed listed as frozen forever while running perfectly well, and the helper processes stopped alongside it stayed stopped forever with it (three Chrome crashpad handlers, four days, state `T`). The daemon now reconciles once a minute: an entry with no processes left is forgotten, a mode that still holds keeps its entry and re-freezes anything that got away, an entry nothing is stopping is dropped, and an entry with both stopped and running processes means the app came back, so the leftovers are freed. Entries carry pids and a timestamp because that last case needs to know which processes are younger than the freeze.
- **A tether counter reading zero looks exactly like a careful month.** The cap is linked to a gateway MAC, and a phone hands out a new one when its hotspot is re-created; when that happened the counter simply stopped counting, and `netmeter tether` reported "0 KB of 50 GB, not on the tether network", which is also what it says when you are sitting at home. Three weeks went by. It now warns when the linked network has not been seen at all, or when a period more than two days old has counted nothing.
- **One long line in an NSMenu sets the width of the whole menu**, and it stays set: the item does not truncate, it stretches, and every row below it inherits the space. A single 100-character tether warning was enough to double the menu's width. Anything whose length is not fixed by the layout (a warning, a network name, a list that grows an entry at a time) goes through `addDisabledWrapped`, which breaks it near 48 characters. Wrapped text has to be an `attributedTitle`, because a plain `title` swallows newlines; that forfeits the automatic disabled dimming, so the colour and font are set by hand, and the break is `U+2028` rather than `\n` so `headIndent` can hang continuations under the text instead of under the glyph.
- **Both halves log to `~/.netmeter/netmeter.log`, and `netmeter log` reads it.** launchd captures stdout and stderr per process, so the daemon's crashes went to `daemon.log`, the bar's to `bar.log`, and a CLI run from a shell wrote its traceback to a terminal nobody kept. Three of those sat unread in `bar.log` for a week. One tick raising no longer kills the daemon either: it lands in the log and the next tick runs.
- Freezing is whole-app (SIGSTOP), not network-only. Per-app network blocking requires an Apple-signed Network Extension, which a script cannot provide.
- The engine's `FRIENDLY` list maps nettop's truncated names; Claude Code sessions appear as their version number (e.g. `2.1.220`).

## Limits

- **Content-type filtering is out of reach.** netmeter sees bytes per process and nothing else, so it cannot tell an image from an API call and cannot "load the page but not the pictures". That needs a Network Extension for apps, or a browser extension for the browser: `declarativeNetRequest` can block image, media and font requests inside Chrome, and `meeting-mode-extension/` is the pattern to copy if that gets built.
- macOS only. Per-app *blocking* is out of reach (it needs an Apple-signed Network Extension); what is here instead is freezing, duty-cycle throttling, and a burst cap, all of them acting on the process rather than on its sockets.
- Sub-5-second processes can slip between samples.
- System daemons deliberately have no freeze switch in the per-app list (`PAUSE_DENY`). Claude Code used to be on that list too and came off with solo mode on 2026-08-28: Pause All means everything, so the sessions get a switch like anything else. Freezing one stops the session until you switch it back on.
- `~/.netmeter/throttled.json` records what is throttled and at what percent; `~/.netmeter/paused.json` records why each app was frozen (`manual`, `lowdata`, `cap`, `all`), which pids were stopped and when, which is what lets `lowdata off` unfreeze what low data froze and leave a hand-paused app alone, and what lets the daemon tell a live freeze from a dead one.
