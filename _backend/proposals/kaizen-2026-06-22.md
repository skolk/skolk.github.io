## Edit 1 — Bootstrap a minimal transcript-fixture harness so spec edits become gatable

**Lens:** kaizen (prerequisite for the iron rule to mean anything in this repo)
**Motivating signal:** Last run's 4 edits all un-landable for want of `evaluations/` +
`promotion-gate.sh` (STATUS 2026-06-20 Kaizen line; `kaizen-2026-06-20.md` Landing sequence
assumes a harness that does not exist). The iron rule requires a fixture per edit; this repo has
no place to put one. This is the gating dependency for Edits 2+ and every future kaizen run.
**Target:** new files under `_backend/evaluations/` (does not edit any existing spec; additive).

### Diff
New tree (nothing edited, all created):

```
_backend/evaluations/
  README.md           # what a fixture is, how runner reads it, what PASS means
  runner.sh           # reads each fixtures/*/spec.txt, greps the agent's recorded output
                      #   transcript against RECORDED_MUST_MATCH / RECORDED_MUST_NOT_MATCH,
                      #   exits non-zero on any miss. No network, no agent invocation — it
                      #   asserts over a committed transcript, so it is deterministic and
                      #   sandbox-safe (pure grep, the one thing the sandbox has never denied).
  fixtures/
    .gitkeep
```

`runner.sh` contract (the load-bearing behavior, stated so the guarding fixture below can
check it): for each `fixtures/<name>/`, read `assertions.txt` (lines `MATCH: <regex>` and
`NO-MATCH: <regex>`) and `recorded.txt` (a committed agent-output transcript). Every `MATCH`
regex must be found in `recorded.txt`; every `NO-MATCH` regex must be absent. Print
`PASS <name>` / `FAIL <name> (<which assertion>)`; exit 1 if any fixture fails.

### Guarding fixture
**New fixture `evaluations/fixtures/harness-self-check/`** — the harness's own smoke test
(drift class: tooling-regression / self-referential). Seeds:
- `recorded.txt`: two lines, `the build ran: [ran: bin/build, exit 0]` and `image refs: clean`.
- `assertions.txt`:
  - `MATCH: \[ran: bin/build, exit 0\]`
  - `NO-MATCH: \[static-read\]`

PASS proves: runner.sh actually reads a transcript, honors both a MATCH and a NO-MATCH, and
exits 0 only when both hold. This is checkable WITHOUT the sandbox running a build — it is pure
grep over committed text, so it survives the exact sandbox-denial friction that has bitten 4
cycles. If runner.sh is later broken (e.g. stops honoring NO-MATCH), flip the recorded line to
include `[static-read]` and the fixture must go red. That demonstration IS the regression net.

### Risk touched
None directly. Indirectly strengthens R-003 (build-break) coverage by giving the cycle a place
to encode build-verdict contracts. Does not weaken any mitigation.

## Edit 2 — Diagnostician must not emit a build verdict it did not run; sandbox-skip becomes UNVERIFIED, never PASS

**Lens:** criticality (protects the build-is-the-contract invariant; this is the concrete,
text-real form of last run's Edit 1 "main-thread build as hard gate" + Edit 2 "[ran] vs
[static-read] tagging", merged and retargeted)
**Motivating signal:** RATIFIED across 4 cycles. STATUS 08:06Z (sandboxed diagnostician
returned false "no static blockers," would have MISSED the live build break), 17:20Z (same
sandbox OVER-reported "10 broken images" → reconciled to 0), 2026-06-20 04:58Z ("main-thread
hard-step build remains the working mitigation"). Trend line: "sub-agent sandbox cannot run its
core tool" repeats 3x and is the standing mitigation Sean has accepted every cycle (he re-runs
the build in the main thread). The spec text still tells the agent to *skip silently and call
it a note*.
**Target:** `.claude/agents/risk-test-runner.md` · "Check 4: Jekyll build (R-003)" (line ~40)
and the "What to report" verdict vocabulary (line ~50).

### Diff

Check 4, line 40 — before:
```
- If `bundle` is not available in the sandbox, skip with a note. Sean runs this locally.
```
after:
```
- If `bundle` is unavailable or the build cannot actually be executed in this environment, you
  MUST report this check as `UNVERIFIED` — never `PASS`, never `SKIPPED`-as-if-clean. A build
  you did not run is not evidence the build is green. The main thread (or Sean) runs the
  authoritative build; your role is only to flag, never to certify.
- Tag every finding by provenance: `[ran: <cmd>, exit <N>]` when you executed the command and
  saw its exit code, or `[static-read]` when you inferred it from reading files without running
  anything. A `[static-read]` finding is a hypothesis to be reconciled against the main-thread
  build, never a settled verdict — in either direction (a static-read "broken" can be a false
  positive, a static-read "clean" can be a false green).
```

"What to report" verdict line ~50 — before:
```
One section per check. Within each, separate "issues found" from "clean." End with a summary count and a one-line verdict per check (`PASS` / `ISSUES` / `SKIPPED`).
```
after:
```
One section per check. Within each, separate "issues found" from "clean." End with a summary count and a one-line verdict per check, drawn from this fixed vocabulary: `PASS` (you ran the check and it was clean), `ISSUES` (you ran it and found problems), `UNVERIFIED` (you could not run it — e.g. sandbox denied the command — so no clean/dirty claim is licensed). Never emit `PASS` for a check you did not execute. For the build check specifically, only a `[ran: ..., exit 0]` may be reported `PASS`.
```

(No twin file: there is no `commands/` recipe in this repo, so R-005 byte-identity does not
apply. If/when a canonical recipe is introduced, this contract moves there and the twin rule
re-engages.)

### Guarding fixture
**New fixture `evaluations/fixtures/build-verdict-provenance/`** (drift class:
false-green / verdict-provenance). Requires Edit 1's harness. Seeds:
- `recorded.txt`: a simulated diagnostician transcript where the sandbox denied `bundle` and the
  agent (correctly, post-edit) writes: `Check 4 (Jekyll build): UNVERIFIED [static-read] —
  bundle denied in sandbox; main thread must run the authoritative build.`
- `assertions.txt`:
  - `MATCH: Check 4 .*UNVERIFIED`
  - `MATCH: \[static-read\]`
  - `NO-MATCH: Check 4.*PASS`            (a skipped build may NEVER read PASS)
  - `NO-MATCH: no static blockers`       (the exact false-green phrasing from the 08:06Z trap)

PASS proves the edited contract holds: a build the agent could not run lands as UNVERIFIED with
a provenance tag, and the specific false-green strings that slipped through in 08:06Z/17:20Z are
absent. A second recorded variant (`build-verdict-provenance-ran/`) seeds a transcript where the
build WAS run (`Check 4: PASS [ran: bin/build, exit 0]`) and asserts `MATCH: \[ran: .*exit 0\]`
+ `NO-MATCH: UNVERIFIED`, proving the contract does not over-fire when the build genuinely ran.

This fixture is the exact eval that would catch a regression of the false-green behavior — and
it is checkable in a fully sandboxed environment because it asserts over committed transcript
text, not a live build. That is the property that makes it land where last run's could not.

### Risk touched
R-003 (Jekyll build break, Impact 5 — top severity). This edit STRENGTHENS the R-003 mitigation:
it forbids the diagnostician from issuing the false-clean verdict that let `7df2a24` and
`f52248e` reach origin unbuilt. It weakens nothing. The fixture is the new contract-ref R-003
can cite.

## Edits I could not gate (3)

1. **Hardening the cycle against transient API errors (the NEW friction this run).** All five
   agents died on a transient 401 auth error and had to be re-spawned. This is real, recurring-
   risk-shaped fragility, but it is a *runtime/orchestration* property, not spec text. No
   transcript fixture can assert "the orchestrator retried a 401 and survived" — a fixture
   asserts over recorded output, and there is no recorded artifact for a spawn that never
   produced output. **What would make it gatable:** a harness primitive that records
   spawn-attempt / retry / exit events (an orchestration log the runner could assert over,
   e.g. `MATCH: agent .* respawned after transient-401`). That primitive does not exist; until
   it does, the mitigation is a main-thread orchestration habit (retry-on-transient-auth before
   declaring an agent dead), which belongs in the recipe/runbook, not an agent spec. Recorded
   here so the signal is not lost: this is now a 1-of-1 friction; if it recurs it becomes a
   gating candidate the moment the orchestration-log primitive lands.

2. **Synthesis-stage reconciliation + the full four-value build-state enum** (last run's Edits
   3 & 4). No `commands/run-project-cycle.md` exists to hold a synthesis stage or a recipe-level
   enum. **What would make it gatable:** a real recipe file plus a fixture that seeds an
   agent's `[static-read]` count and asserts the synthesis section reconciles it against the
   main-thread `[ran: exit N]` result. Blocked on the recipe existing, not on a fixture being
   designable.

3. **Un-sandboxing the diagnostician so it can build itself** (carried from last run). Still a
   runtime/permission-posture change, not spec text. A transcript fixture asserts what an agent
   *writes*, not that its sandbox now *permits* a subprocess. **What would make it gatable:** a
   harness primitive recording tool-execution permit/deny events. Edit 2 makes leaving it
   sandboxed *safe* (UNVERIFIED, never false-PASS) in the meantime, which is the better posture
   regardless: the main thread should own the authoritative build even if the agent could run
   one.
